# Audit Entry Before Commit

## Statement

The audit log entry must be created and persisted before the transaction commit that it documents. If audit logging fails, the primary transaction must also fail.

## Rationale

Guarantees that every committed state change has a corresponding audit record. If the audit entry could be written after the transaction commit, system failures between the two would create untracked mutations, violating the append-only audit trail requirement.

## Scope

- Applies to: All state-changing operations in the system (BC-AUDIT)
- Bounded Context: BC-AUDIT (Audit & Compliance)
- Entities: AuditLogEntry

## Conditions

- **WHEN** a state-changing operation is executed
- **THEN** the audit log entry MUST be persisted to the database within the same transaction
- **AND** if the audit log write fails, the entire transaction MUST be rolled back
- **OTHERWISE** the state change must not be committed

## Pseudocode

```
function executeWithAudit(operation, entityType, entityId, oldValue, newValue):
    beginTransaction()
    
    auditEntry = {
        entity_type: entityType,
        entity_id: entityId,
        action: operation.action,
        old_value: oldValue,
        new_value: newValue,
        performed_by: currentUser().id,
        performed_at: currentTimestamp()
    }
    
    persist(auditEntry)
    operation.execute()
    
    commitTransaction()
    
    // If persist(auditEntry) or commitTransaction() fails,
    // the entire transaction rolls back
```

## Exceptions

- None — audit logging failure must always cause the primary transaction to fail.

## Related Rules

- INV-AUDIT-001: Audit log entries are append-only; no updates or deletes permitted
- BR-021: All state-changing operations must create an audit log entry

## Related Concepts

- AuditLogEntry: An append-only record of all state changes in the system
